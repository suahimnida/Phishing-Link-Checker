# 1. 기능 요구사항

## 1-1. URL 판별 로직
```
- 사용자가 URL 입력 시, KISA나 OWASP의 보안 문서 검색 혹은 
  블랙리스트에 매치되면 즉시 피싱으로 확정
- 블랙리스트에 없을 시, RAG + ML을 조합하여 추가 검사 진행
- 1차로 URL 문자열의 구조적 특징과 패턴으로 위험 점수 산출
- 2차로 URL 길이, 특수문자 및 숫자 비율, 과도한 서브도메인, IP 주소 형태 도메인, 도메인 길이,
  서브도메인 개수, IP 주소 사용 여부, Punycode 사용 여부, 의심 키워드 포함 여부,
  path 및 query 길이 등으로 판정하여 위험 점수 산출
```

## 1-2. 머신러닝 분류
```
- UCI PHIUSIIL Phishing URL Dataset을 활용해 정상/피싱 데이터 구축 및 모델 학습
- 입력된 URL의 피싱 확률을 예측하기 위해 추출된 특지을 전처리 한 후
  Random Forest, XGBoost, Logistic Regression 등으로 분류 모델 학습
- URL 구조 특징 추출 후 로지스틱 회귀 알고리즘 기준으로 모델 학습
- 학습된 모델로 입력된 URL의 피싱 확률 예측
- 여러 특징 간의 관계를 하습해 정상/의심/피싱 가능성 높음으로 분류
- RAG를 활용하여 KISA나 OWASP의 보안 문서 검색 혹은 블랙리스트를 참고한 공식 출처도 AI 모델에 전달
```

## 1-3. RAG
```
- 모델의 예측 결과와 주요 특징과 함께 피싱으로 판단된 원인, 위험 요소, 해당 사이트 신고, 2차 보안 설정,
  피싱 사이트에 접속하였을 경우 대처방법 및 사용자에게 권장하는 조치에 관한 내용을 AI 언어 모델에 전달
```

## 1-4. AI 리포트 생성
```
- AI 모델이 전달받은 내용들을 포함하여 분석 결과를 바탕으로 해당 URL에서 발견된 위험 요소와 점수,
  피싱으로 판단한 판정 근거를 자연어 형태의 보안 분석 리포트로 생성
```

## 1-5. API 및 데이터 구조
```
- 백엔드에서 POST /api/v1/analyses로 분석 요청, GET /api/v1/analyses/{analysis_id}로 결과 조회
- POST /api/v1/clients로 브라우저 UUID 발급
- 응답 필드 고정 (프론트에서 결과 화면 바로 확인 가능): URL, 분석 ID, verdict, confidence,
  risk_score, risk_level, 각 탐지 결과, AI 분석 결과, - RAG 결과, extracted_features, similar_cases
- blacklist: {matched, match_type, source} — KISA 블랙리스트 조회 결과
- rag: {matched, source, evidence} — RAG 검색 결과 (KISA 블랙리스트 조회 결과 자체가 아니라,
  RAG가 참고한 문서/근거를 담는 필드로 정의 필요 — 현재 설계상 blacklist와 역할이 겹치지 않도록 구분 확인 필요)
- model: {status, risk_score, label} — ML 모델 결과 (추후 모델 연동 대비 필드 사전 확보)
- extracted_features: {}, similar_cases: [], ai_analysis 필드에 RAG/특징 추출 결과 반영
- id 필드는 문자열 타입으로 응답
```

## 1-6. 사용자 세션 / 로그
```
- UUID는 백엔드에서 발급, 프론트는 로컬스토리지에 저장만 함
  (분석로그 조회하는 방식은 저는 uuid 발급해서 브라우저 로컬스토리지에 저장해서 같은 브라우저로 재접하면 볼 수 있게 하는 방식)
- 같은 브라우저 재접속 시 UUID로 이전 분석 로그 조회 가능
- 최근 링크 검사 내역 조회 기능
- 비공개 분석용 비밀번호 입력 UI는 프론트에서 구현, 값 전달만 담당
- 비밀번호의 해시 저장 및 검증(접근 제어)은 백엔드에서 처리
```

# 2. 비기능 요구사항

## 2-1. 보안 / 안전성
```
- URL 분석 시 실제 사이트에 접속하지 않고 문자열 패턴만으로 분석 (악성 사이트 접속 위험 차단)
- 비공개 분석 비밀번호는 평문이 아닌 해시로 저장하고 백엔드에서만 검증 (프론트는 값을 알 수 없어야 함)
- CORS 설정 완료 — 프론트엔드(localhost:5173)에서의 요청만 허용하도록 제한
```

## 2-2. 신뢰성 / 데이터 보존
```
- SQLite DB 파일 생성 후, 서버 재부팅 시에도 기존 ID·데이터가 유지되는지 보존성 확인
```

## 2-3. 인터페이스 일관성 / 유지보수성
```
- API 주소 체계를 /api/v1/...로 통일 (버전 관리·일관된 네이밍)
- 응답 구조에서 blacklist(KISA 조회) / rag(RAG 검색) / model(ML 결과)을 역할별로 명확히 분리
```

## 2-4. 개발 환경 / 배포 구성
```
- 프론트엔드 개발 서버 주소는 http://localhost:5173 사용
- 프론트엔드/백엔드를 Git 브랜치로 분리해서 개발
- FastAPI로 백엔드 서버 구축, KISA 데이터 로드 후 GET/POST 동작 여부 확인 (개발 검증 절차)
```
